# Live FlexBuffers layouts

Component definitions and scene instances are binary FlexBuffers data. The runtime interprets a versioned typed contract directly from FlexBuffers through the Rust Serde adapter; no JSON representation is used in authoring, transport, persistence or activation. The existing Automerge binary protocol carries document changes. UI primitives, clipping, responder delivery and GPU hosts remain shared.

## Representation

`otrios-layout-v1` contains a table of component templates plus one instance tree. Templates define primitive nodes, parameter declarations, typed expressions, child slots, responders and switch semantics. Instances select a template, carry stable IDs, a float frame `[x,y,width,height]`, parameter overrides and child instances. The initial templates are Screen, Text, Panel, Switch and Graph; their definitions are in the committed `crates/otrios-core/src/dashboard/default.flex`, not Rust component factories.

Numeric frames encode as typed float vectors; RGBA values encode as typed unsigned vectors. FlexBuffers supplies runtime type tags. The separate contract enforces required fields, expression result types, units, versions and bounds; it is not a schema generated by FlexBuffers itself. Serde is an already-transitive dependency, now exposed through an optional interface feature for typed direct binary decoding.

Expressions support typed literal Number/Boolean/Text/Color/Series, declared parameter references, instance width/height, explicit application bindings, addition/subtraction/multiplication and typed conditionals. Bindings are an enum: enabled, title, touch label, samples, sample presence and last sample, and a scoped typed local binding used by the shell. There are no arbitrary scripts, property-path evaluation or user-provided native callbacks. The known toggle action reaches current app state through the existing responder chain. New primitive types or actions require a code release. The current responder contract also provides explicit shell navigation, focused-field and keyboard-key actions; system assets use those within the local host, without CRDT navigation state.

Panel is Canvas + Superellipse + a child slot. Switch is Canvas + Superellipse + Text + a nested track Canvas/Superellipse/Circle, with an activating responder and accessibility metadata. Graph uses primitive Text, Superellipse grid lines, a series-bound Path and marker Circle. Slots insert child instances as primitive Canvas children. Template-local node IDs reserve stable ranges under each globally unique instance ID.

The bootstrap asset is generated by `dashboard-layout seed` from `layout_seed.rs`, an authoring fixture, and checked for exact binary agreement in tests. That fixture is not evaluated by the runtime. Supplied layouts replace it as data. The bootstrap is 10,490 bytes. A published layout is one atomic Automerge byte-scalar register. Concurrent full-layout changes have Automerge's deterministic register winner; independent node edits are not merged yet. Earlier drafts remain in retained history. The initial editor is a command-line binary tool, not a visual editor.

## Author and publish

Build the tool with the pinned toolchain:

```sh
cargo build --release -p otrios-dashboard --bin dashboard-layout
```

Fetch the current binary draft and its base revision, inspect it, make edits, then publish:

```sh
target/release/dashboard-layout fetch http://127.0.0.1:8876/layout work/dashboard.flex
target/release/dashboard-layout inspect work/dashboard.flex
target/release/dashboard-layout frame work/dashboard.flex 2 80 208 424 240
target/release/dashboard-layout text work/dashboard.flex 6 1 'OTRIOS  /  LIVE BINARY LAYOUT'
target/release/dashboard-layout color work/dashboard.flex 3 2 1F3246FF
target/release/dashboard-layout publish work/dashboard.flex http://127.0.0.1:8876/layout
```

Create the `work` directory first if needed. `inspect` lists template parameter keys/types and instances. `frame FILE INSTANCE X Y W H`, `text FILE INSTANCE PARAM TEXT`, `number FILE INSTANCE PARAM NUMBER` and `color FILE INSTANCE PARAM RRGGBBAA` edit typed fields in the binary file. `add-text FILE NEW_ID PARENT_ID X Y W H TEXT`, `add-panel FILE NEW_ID PARENT_ID X Y W H` and `remove FILE INSTANCE` change structure. These two convenience constructors select the bundled Text/Panel template IDs; custom templates can be authored with the public typed contract. `export FILE` starts a draft from the bootstrap; `fetch URL FILE` starts from the deployed configuration. Draft edits do structural validation; publication performs full scene/type/geometry validation before activation.

The tool writes `FILE.base` beside a fetched/exported draft. Publishing sends that expected revision and updates the base only on success. A stale edit gets HTTP 412; fetch current data and reapply edits instead of silently overwriting another publisher. The CLI uses literal loopback HTTP addresses only. Remote editors can use the same binary endpoint over the existing private Tailscale HTTPS origin; no remote JSON editor is added.

`GET /layout` returns exact editable FlexBuffers bytes (the underlying CRDT layout when a read-only monitoring presentation is active) with an ETag and download filename. `POST /layout` requires `Content-Type: application/octet-stream` and `If-Match: "LAYOUT_ID"`. Browser origin checks apply. The room locks publication, checks the base, validates a candidate, flushes its document to disk, swaps the active replica and announces changes over the existing WebSocket stream. Normal touch state, counters and samples remain intact. Layout changes do not increment the touch counter or change code-release IDs.

The layout ID is SHA-256 of `OTriOS\0layout\0v1\0` plus exact layout bytes. It proves byte identity, not authority. This is not a cross-encoder canonicalization or signature claim. The same trusted tailnet editors that can edit demo state can publish bounded declarative layouts. Native executable releases retain their separate pinned-signature boundary.

## Activation, caching and compatibility

A replica validates a full layout before writing its binary register. Materialization puts the chosen layout blob into a complete immutable v1 view snapshot. Each host expands that layout with current application bindings into a validated primitive scene and publishes the whole root. The active layout model is retained in an Arc and reused while its exact bytes remain unchanged; ordinary state updates re-evaluate bindings without decoding the layout again. Snapshot payloads are complete owned byte buffers and compiled scene nodes are owned typed values. This is not zero-allocation, mmap access or Linux shared memory.

The original seed has no layout field and retains its history and golden snapshot ID. The optional layout blob binds configured scene construction into subsequent snapshot hashes. The v1 application-node records remain for state compatibility and bindings; their old widget rectangles are not the hit-test source. Painting, input and browser semantic controls use the expanded primitive scene. A scene snapshot read from bytes includes enough layout data to reproduce that construction under the same interpreter release.

Validation bounds include 128 KiB per layout, 32 templates/parameters per template, 128 instances, 512 template and expanded nodes, expression depth 12, binary traversal depth 48 and 32,768 visited values. Literal series allow up to 256 points; the demo state binding retains 32 samples. Scene depth remains bounded to 16. Unknown fields/types/schema, duplicate identities/parameters, missing component references, malformed/truncated buffers, invalid geometry and wrong binding/property types are rejected. Qualification checks both switch states and normal appended sample values. Each materialization still validates its actual result; this is a bounded trusted development interpreter, not a proof that arbitrary expressions are valid for every hypothetical application schema.

Rejected publication leaves the saved document and displayed root intact. The server's expected-revision check protects HTTP publication; direct offline CRDT peers still follow the documented whole-register merge semantics. A larger design can be edited locally as a draft and activated in one publication. Per-node collaborative editing, a shared draft workspace, a visual primitive-based editor, general binding schemas, layout migration and conflict UI are deferred.

## Evidence

Tests exercise typed-vector binary encoding, exact bootstrap round trip, data-only geometry/text changes, primitive template changes, nested slots, retained snapshots, persistence, both-state qualification, malformed input, concurrent CRDT layouts and ordinary state edits. A real child-process test runs the CLI, publishes over HTTP, observes WebSocket push, races two publishers against one base revision (one succeeds), rejects bad/stale/cross-origin/oversized updates and recovers the layout after server restart. See [validation checkpoint](experiments/dashboard-validation.md) for actual hardware/browser evidence.

A separate replaceable [monitoring presentation](MONITORING.md) can display complete binary primitive views without accumulating metric windows in the collaborative layout register. Clearing it reveals the retained editable layout.

## Proposed typed selectors and module roots

[RFC 0003](rfcs/0003-module-roots-and-state-selectors.md) proposes a versioned successor to enum/local bindings: typed state selectors shared by UI properties, identity-based collection targets, and separate UI/State subscriptions per module. It defines navigation through opaque UI/State references and distinguishes CRDT metadata replication from value-level repaint. The current v1 interpreter and whole-room replication do not implement that contract.
